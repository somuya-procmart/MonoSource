## Phase 0 — Repository & architecture audit ✅
Report: `00-phase0-architecture-assessment.md` · ADRs: `adr/` · Decisions: `DECISION_REGISTER.md`

## Phase 1 — Foundation ✅ (dev-grade auth)
Built and tested: independent NestJS API + Next.js web; SQL migrations; tenant isolation by Postgres RLS; platform → customer creation; configurable org levels + CSV org import (server-scoped plant identity); roles/permissions with org-subtree data scope; append-only audit log; rate limiting, validation, upload checks.

## Phase 2 — Catalogue & ARC engine ✅ (AI path implemented but not exercised against a live provider)
Built and tested: catalogue + per-ERP material codes + CSV import (incl. `spec_*` columns) + FTS search; **item versions** (who/when/what), **images and datasheets** (byte-sniffed PNG/JPEG/WebP/PDF, ≤5 MB, SVG refused, served sandboxed with nosniff, tenant-scoped); suppliers with per-ERP vendor codes (no auto-merge); contract upload for **CSV, Excel (rules, values not formulas, `sheet!row` refs) and PDF (AI-assisted)** → stored original → extraction run (provider, version, prompt version) → normalised lines (raw kept) → **full 5-step match ladder incl. approved equivalent codes** → human review → validation → approval → publication. Failed or unsupported extractions keep the contract as a draft with the reason, and can be **re-run**; contract header can be set/confirmed by a person (AI header is only a suggestion).
AI guard rails (unit-tested with a mocked model): document text is treated as data; JSON-only output; every value must literally appear on the cited page or the line is flagged; confidence capped at 0.85; invalid output becomes a failed run, never a result; nothing is ever auto-approved.
Not verified: behaviour against the real Anthropic API (only a mocked client is tested); scanned PDFs (no OCR); `.xlsm`/macros are refused; very large workbooks are capped (5 sheets, 5,000 rows each).

## Phase 3 — Buyer experience ✅
Done: search with live suggestions, **product detail page** (images, datasheets, specs by category template, contract price, how it will be bought, version history for staff), cart with routing preview, requirement creation and tracking, and **Ask MonoSource** (guided buying): reads values from your sentence, asks required attributes first then the most useful one, shows only existing catalogue values, keeps items with an unrecorded spec as "unknown" instead of guessing, prices and coverage come from the same engine as search. It is deterministic (no AI needed); an LLM interpreter could be added later behind the same endpoint.
Not done: free-text understanding beyond catalogue values (synonyms, other languages), saved conversations.

## Phase 4 — Routing & sourcing ✅ (core) · approvals/consolidation partial
Done and tested: per-line routing; allocation register with joint approval; ARC eligibility and ranking; ARC-vs-direct policy gate; **RFQ** (needs customer's minimum-quotes rule; invites only active suppliers with a vendor code on the plant's ERP; ProcMart may bid only if policy says so); **quotes** (invited suppliers only, one each, UOM must match, entered by ProcMart ops until the supplier portal exists); **comparison** on landed unit cost (price + freight, excl. GST) with L1 and % vs L1; **recommendation** by ProcMart ops; **award by the customer's approver** (`buying:approve`) — non-L1 needs a written reason (also enforced by a DB constraint); award creates a Model 3 stream and a PR through the outbox; **exception queue** (routing exceptions, blocked PRs) with mandatory resolution note; sourcing + exceptions screens.
Not done: ARC split across contracts, demand consolidation, ARC-ranking override approval (APR-03), off-contract approval (APR-04), valid Model 3 award reuse (step 4), tiered competitive thresholds beyond "minimum quotes", multi-approver chains, supplier-facing quoting (Phase 5 portal).

## Phase 5 — Orders & supplier operations ✅ (ERP side simulated; comms simulated)
Done and tested: **supplier portal** (own orders only; no model/fee visibility): acknowledge (accepted / partial / declined, can't over-commit), dispatch in several lots with ASN/carrier/tracking/invoice/e-way bill, invoice submission (only after GRN), RFQ list and self-service quoting (only invited RFQs, never other suppliers' prices); **order status derived from quantities** (partial dispatch, partial receipt, GRN); simulated **GRN** with accept/reject quantities; simulated PO release and payment; **exceptions** auto-raised for partial commitment, declined order, goods rejected, unresponsive supplier, blocked PR; **follow-up automation** with customer-configured intervals/channels/escalation count (off until configured — no default SLA), failures recorded, one escalation per stream, comms provider port (simulated provider only); buyer order page with stepper, shipments, follow-ups; supplier users redirected to the portal.
Not done: real email/WhatsApp/call providers; supplier contacts beyond one email/phone; replacement/return/cancellation workflows (Q11 — facts are recorded and an exception raised, a person decides); ASN → SAP push; invoice verification mirror beyond submitted/paid; supplier performance scoring; supplier onboarding flow and documents; password reset / invite emails for supplier users.

## Phase 6 — Control tower & analytics ✅ (MonoSource-originated data only)
Done and tested: **documented metric registry** (17 metrics, each with definition, source tables and caveat; a test fails if the API returns a metric without a definition); group and plant dashboards with scope selector and period; KPI tiles with in-page definitions and **drill-down to the underlying records**; routing mix, value by commercial model, "contract existed but was not used" reasons, order pipeline, open exceptions, fee-base value (no rates applied), plant comparison, supplier performance (fill rate, rejection, acknowledgement time, on-time dispatch, unresponsive), contract utilisation, expiring contracts, category performance; **operational MIS CSV export** (audited, formula-injection safe); data scope enforced (a plant user only sees their plants; contract data needs `contracts:read`); tenant isolation tested.
Honest limits: no SAP PO feed, so true off-contract/leakage (BRD 9.7) and total-spend coverage are **not** measured — the tile says "contract existed but was not used" instead; RFQ "competition spread" is **not** savings against a baseline (baseline method undefined, BR-FEE-08/Q6); GRN/PO/payment are simulated; no on-time-delivery against need-by yet; no scheduled reports, alerts or trend charts over time.

## Known issues / limitations
- Local password auth only; JWT secret default is dev-only (production refuses to boot without `JWT_SECRET`).
- Utilisation = sum of requirement-line quantities per contract line (committed). No SAP PO feed, so no ordered/received/invoiced ledger yet (BRD BR-UTL-03).
- Org tree for a scoped user shows only their subtree (no ancestors).
- No four-eyes rule (uploader ≠ approver) yet — decision needed.
- Org import creates ERP systems as kind `sap`; set `mock-sap` first for simulation.
- Contract "expired" status is not auto-transitioned (no scheduler yet); expiry is enforced at query time.
- Storage is local disk.
- Web UI is functional, not designed; no automated UI tests.
